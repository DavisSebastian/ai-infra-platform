The big picture

What we are building, in one diagram.

A small server that hosts an AI model. You send a question, and the answer streams back word by word, like ChatGPT. It speaks the same API format as OpenAI (/v1/chat/completions), so later weeks can swap in vLLM without changing the client.

The files, and the Spring-style split between them:

1The model writes one token at a time

The idea everything else builds on.

An LLM does not write a whole answer in one go. It looks at everything so far, guesses the next token (roughly a word or word piece), adds it to the text, and repeats. A 200-token answer means 200 separate passes through the model.

Two waits, not one

WaitNameWhat it is
Until the first word appearsTTFT (time to first token)The model reads your whole prompt first. Fixed cost, paid once. Queueing time adds to it
Between later wordsITL (inter-token latency)One full pass through the model per token
Measured on my Mac

Same model, same machine: a 10-token answer ran at 47 tokens/s, a 46-token answer at 79 tokens/s. The model did not get slower. Each request pays a fixed startup cost (about 0.1 s here) plus about 0.01 s per token, so short answers look slower on average. That is why one "tokens/s" number can mislead, and why we measure TTFT and ITL separately.

TokensTime (0.1 s + 0.01 s × tokens)"tokens/s" shownShare spent on the fixed cost

It works like a taxi fare: a fixed fee to get in, then a price per km. A short ride makes the per-km price look high.

2Chat format to numbers

What encode() does, step by step.

The model only continues text, and only understands numbers. So a chat message goes through two conversions before the model sees it.

Conversion 1: the chat template

During training, conversations were written as plain text with marker words showing who speaks. The template rebuilds that layout. This is the real text my 6-word question became:

<|im_start|>system
You are Qwen, created by Alibaba Cloud. You are a helpful assistant.<|im_end|>
<|im_start|>user
Say hello in five words.<|im_end|>
<|im_start|>assistant

The last line is the cue. The text stops exactly where the assistant starts speaking, so the model's next guess is the first word of the answer (that is what add_generation_prompt=True does). The system message was added by the template, not by me.

Why changing MODEL_ID needs no code change

Each model family has its own markers (Llama uses <|start_header_id|>, for example). The right template ships inside the model's files, so apply_chat_template picks the correct one automatically.

Conversion 2: tokenizing

The tokenizer has a fixed dictionary of about 150,000 word pieces, each with an ID. Real output from my run:

IDPieceNotice
45764'Say'
23811' hello'The leading space belongs to the word
4236' five'Common words are one token
13'.'Punctuation is its own token
1207 + 16948' Q' + 'wen'Rarer words get split
151644'<|im_start|>'A whole marker is a single token

The same piece always gets the same ID (' are' is 525 both times it appears). 35 numbers in total: that is where prompt_tokens: 35 comes from. Going backwards is tokenizer.decode(ids).

Java analogy

The template is a MessageFormat the model dictates. The tensor is a typed int[][] that can live on a GPU, which is why .to(device) is needed: input and weights must sit on the same hardware.

3Prompt tokens vs completion tokens

Two halves of one request, priced and timed differently.

prompt_tokens

Everything that goes in: your question plus the hidden system message and markers. 35 in my example.

completion_tokens

Everything that comes out: the answer the model wrote. 10 in my example.

How it is processedCost
PromptAll at once, in one passCheap. It is the fixed part of TTFT
CompletionOne token at a timeExpensive. Each token is a full pass (ITL)

That is why paid APIs charge more per output token than per input token. It also explains why long chats get slower and pricier: the server remembers nothing, so the client resends the entire conversation every turn, and prompt_tokens keeps growing.

4Load once, cache forever

Where the model comes from, and why startup matters.

There is no separate "download" step. from_pretrained("Qwen/Qwen2.5-0.5B-Instruct") does both jobs:

Java analogy

Maven checks ~/.m2 first and only goes to Maven Central when a JAR is missing. Hugging Face Hub is Maven Central for model weights.

The cache holds the tokenizer files (dictionary and chat template), config.json, generation_config.json (default sampling settings, which is why answers vary), and model.safetensors (the weights, the actual "brain").

In the server, loading happens once in lifespan, before any request is accepted, like a heavy singleton @Bean:

@asynccontextmanager
async def lifespan(app):
    app.state.llm = LLM(MODEL_ID, DEVICE)     # runs once at startup
    app.state.gen_lock = asyncio.Lock()
    yield                                      # server handles requests here
DevOps preview (Docker, step 7)

Inside a container, the cache is lost whenever the container is deleted, so every fresh container would re-download the model. For the 16 GB Llama on a paid GPU box, that hurts. The fix is to keep the cache outside the container as a volume.

Hardware is picked automatically (cuda NVIDIA, mps Apple GPU, cpu). On my Mac the tiny model ran at 37 tokens/s on CPU and 79 on the Apple GPU: only about 2x, because the model is tiny and CPU and GPU share one memory.

5The freeze bug

Step 2: calling the model directly inside async def.

@app.post("/v1/chat/completions")
async def chat_completions(...):
    result = llm.generate(messages, max_tokens)   # slow, synchronous, never lets go of the thread

This is Week 1's /blocking endpoint again. async def only helps if the code inside lets go of the thread (at an await). generate() never does, so the single event-loop thread is stuck for the whole answer.

Request A is generating. Request B asks /health at 0.5 s.
Event loop thread
stuck inside generate() for the whole answer
/health request
waiting... waiting... waiting...
0 srequest B sent at 0.5 sanswered at about 5.1 s
Measured

/health normally answers in about 1 ms. During generation it took 4.6 s and, on a second run, 4.8 s, even though it does no work.

Why it is worse than slow

Load balancers and Kubernetes poll /health every few seconds. If it does not answer in time, the server is marked dead and restarted, killing everyone's in-progress answers. One long question can take the whole server down.

6The fix: a thread and a queue

Step 3: move the slow call to its own thread, and stream the answer.

The generation thread is the producer: it puts each new word into a queue. The event loop is the consumer: it takes words out and sends them to the client. In between words, it is free.

One word, in detail

Why "leave a note" instead of writing to the queue?

The queue belongs to the event loop thread. If two threads touched it directly they could step on each other. call_soon_threadsafe is the safe doorway.

Same test as before, after the fix
Generation thread
generate() running on its own thread
Event loop thread

Blue = sending a word. Purple = answering /health in the gap. Almost all of the time, the event loop is idle and available.

Measured

/health during a long generation: 4.6 s before, 0.00 to 0.01 s after. Both streaming and non-streaming paths.

Three details that matter

  • Use the async streamer. The plain TextIteratorStreamer has a blocking read. A normal for loop over it freezes the event loop again, even though generation is on another thread. AsyncTextIteratorStreamer is async for-friendly.
  • The non-streaming path got a one-line version of the same fix: await asyncio.to_thread(llm.generate, messages, max_tokens).
  • Crash safety net. If generate() crashes (say, out of GPU memory), nothing would put the END marker in the queue and the request would hang forever. The thread catches the error, stores it, and ends the stream itself.
Java analogy

A worker thread filling a BlockingQueue while a Netty or WebFlux handler reads it, except the reader awaits instead of blocking.

Which thread runs start_stream()?

The event loop. Only the thread's target function (_run) runs on the new thread. thread.start() is like pressing the washing machine's start button: you press it quickly, then walk away.

stream = llm.start_stream(...)      # event loop: encode(), create queue, thread.start()  (about 1 ms)
                                    #   _run() -> model.generate() runs on the NEW thread (seconds)

It must run on the event loop because AsyncTextIteratorStreamer records "the running event loop" when created, and the generation thread uses that to deliver words later.

7What await really does

Including the confusing nested one, await stream.wait().

await X does two things at once:

For this requestFor the server
"Pause me here until X is finished.""The thread is free to serve other requests meanwhile."

So it does not mean "skip this". It means "wait for it, without holding the thread hostage". Think of a waiter who takes your order to the kitchen and serves other tables until your dish is ready.

Why await stream.wait() exists

generate() puts the END marker in the queue before it returns. So there is a tiny gap where the endpoint knows the stream ended but the thread has not clocked out yet:

Without wait(): the finish_reason could be wrong (the token count is not set yet), a crash would go unnoticed, and the lock could be released while the thread is still running. It is a "make sure the worker has clocked out" step, like thread.join() before reading a result.

The nested await is just function calls

It looks confusing, but it is the same as A() calling B() calling C() in Java. Each await says "I cannot continue until the thing below me finishes", and the pause passes up through every level.

async def wait(self):
    await asyncio.to_thread(self._thread.join)   # not self._thread.join(): that would block the event loop
    if self.error:
        raise self.error
The rule of thumb for this whole step

Blocking call (generate, join, anything slow that is not async)? Put it on a worker thread with asyncio.to_thread, then await it.

8Why a lock, if there is only one event loop?

One event-loop thread does not mean one request at a time.

The event loop switches between requests at every await. That is exactly how 500 requests were "in flight" on one thread in Week 1. And each streaming request starts its own generation thread, so without a lock, 16 requests would run 16 generate() calls on one GPU at once.

The lock protects the GPU and the model, not the event loop. Running two generations at once with plain Hugging Face gives no speedup and risks running out of memory. Serving many users properly means batching them together, which is what vLLM does in Month 3.

Measured

Two identical requests sent at the same moment: the first finished in 0.60 s, the second in 1.33 s. The second took about twice as long purely from waiting. With 16 users the last one waits behind 15. That growing wait is Little's Law from Week 1, and the baseline Month 3 will beat.

Java analogy

A Netty event loop in front of one printer. The loop can accept many clients, but print jobs need a Semaphore(1) or the pages get mixed up. The async version just does not block the loop while waiting.

9One streaming request, start to end

Everything together, in order.

A surprise in step 3

When chat_completions() returns the StreamingResponse, zero tokens exist and the lock is not held. Calling stream_chunks(...) only creates a paused generator (like a Reactor Flux: nothing runs until someone subscribes). The work starts when Starlette begins pulling events from it. That is also why a request stuck behind the lock has already received its 200 headers, but no words yet.

What a client sees on the wire (OpenAI streaming format):

data: {"choices": [{"delta": {"role": "assistant", "content": ""}, "finish_reason": null}]}
data: {"choices": [{"delta": {"content": "Hello! "}, "finish_reason": null}]}
data: {"choices": [{"delta": {"content": "How "},    "finish_reason": null}]}
   ...
data: {"choices": [{"delta": {}, "finish_reason": "stop"}]}
data: [DONE]

Each event carries only the new piece (delta); the client glues them together. finish_reason is "stop" if the model finished itself, or "length" if it hit max_tokens. That cap matters for cost: the server never allows more than MAX_NEW_TOKENS, so one request cannot hold the GPU for minutes.

10The disconnect problem

Found by measuring. This is what step 4 fixes.

What happens when the client closes the tab halfway through? My first guess was that wait() would raise an error and notice. That was wrong. I tested it instead of assuming:

A long generation, client disconnects at t = 3.6 s
Client
connected, receiving words
Lock
heldreleased, nobody holds it
Generation thread
generatingstill generating for nobody (4.4 s)
2.65 s: generate() starts3.64 s: disconnect8.08 s: generate() ends

wait() cannot detect it for two reasons: it is never called, and it only raises self.error, which is set when generate() itself crashes. A client leaving is not a crash inside the thread.

Two real problems

1. Wasted GPU time. Here, 4.4 seconds of generation for an answer nobody reads. On a rented GPU you pay for that.

2. The lock lies. It was released at 3.64 s while the thread ran until 8.08 s. A request arriving in that window would start a second generate(), exactly what the lock was meant to prevent.

The plan for step 4

A thread cannot be killed from outside. It has to stop itself when asked.

  1. Give each Stream a stop flag.
  2. Pass generate() a StoppingCriteria: a hook it calls after every token, which checks the flag and stops early.
  3. In stream_chunks, catch the cancellation and set the flag.
  4. Wait for the thread to really finish before releasing the lock, so the lock stays honest. (Tricky: that wait happens while the task is being cancelled.)
Java analogy

Thread.interrupt() plus checking Thread.interrupted() inside the loop. You cannot force-stop a thread. You set a flag, and the loop cooperates.
