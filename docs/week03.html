The Gateway: a fast no beats a slow yes

Week 2's model server does one generation at a time, and it can't say "I'm full". With 16 users at once, the last one waited 56 seconds on an RTX 4090. This week a gateway sits in front of it: it limits each client, bounds the line, and turns everyone else away in milliseconds.

1A streaming proxy

Step 1: pass each chunk through the moment it arrives.

The gateway makes its own request to the model server and relays the answer. The one rule: never collect the whole answer first. If it did, the first word would arrive only when the last one does, and streaming would be pointless.

It forwards raw bytes without parsing the SSE events: no added latency, nothing to get wrong. One pooled client is created at startup and reused, like the model in Week 2.

Measured

200 users against a fake model server: median first word 35 ms direct, 33 ms through the gateway with aiohttp. With httpx: 2.9 s, so aiohttp it is.

Gotcha

A first run showed aiohttp at 458 ms. The upstream pool had 100 connections and 200 users were queueing for them. Pool exhaustion looks exactly like a slow client.

When a client leaves, the gateway closes its upstream request, and the model server's stop flag from Week 2 fires. A test proves it: the fake model server counts the stream as cancelled, not finished.

You need both. Sixteen polite clients, each within their own limit, still build Week 2's 56-second line. One greedy client, without a rate limit, can take every place in that line.

3The token bucket

Step 4: bursts allowed, average capped.

Each client has a bucket of up to capacity permits that refills at refill rate per second. A request takes one permit; an empty bucket means 429. Capacity 10 and 1 per second means "10 at once, then one a second".

No timer runs in the background. Each check computes the refill from the time since the last check:

elapsed = max(0, now - updated_at)
permits = min(capacity, permits + elapsed * refill_rate)
allowed = permits >= 1  (take one if so)
store permits AND updated_at = now, together
Found by breaking the code

The first test set missed two bugs: storing the refilled permits with the old timestamp counts the same seconds twice (the limit leaks), and a clock that jumps back produced a negative refill. Both have tests now. Rule: permits and timestamp are one piece of state.

4The race, and Lua

Correct arithmetic, wrong result.

Two gateway replicas must share one bucket per client, so it lives in Redis. The obvious version reads the bucket, computes in Python, and writes it back: two Redis commands with an await between them.

Limit 10, 50 requests at once, 5 runsAllowed
Naive: read, compute, write50 of 50, every run
Lua script: one atomic commandexactly 10, every run

All 50 read "10 permits left" before any of them wrote. Redis runs a Lua script as one uninterruptible command, so the read-compute-write can't be split. The naive version even reuses the correct pure function: the only bug is the gap.

Java analogy

if (map.get(k) > 0) map.put(k, ...) vs AtomicInteger.decrementAndGet(). A check followed by an act is a race; make it one operation.

5Pools and timeouts

Step 3: one Redis pool, and a deadline on every wait.

One BlockingConnectionPool is created at startup. When all connections are busy, the next caller waits up to 0.5 s for one instead of failing at once, the same as HikariCP's connectionTimeout.

Measured

A fake Redis that accepts connections and never answers. With a socket timeout, /health gives up after 0.5 s. With the timeout removed, it hung until the test client quit at 10 s. One slow dependency freezes every request that touches it.

6Backpressure

Step 5: one doctor, two chairs in the waiting room.

  1. Cap in-flight requests at what the model can do: 1 for the Week 2 server.
  2. Bound the queue. Little's Law sizes it: acceptable wait ÷ time per answer. About 10 s ÷ 3.7 s on the GPU gives 2.
  3. Shed early. Queue full on arrival: 503 at once.
  4. Time out the wait. Still queued after 10 s: 503.
  5. Drop leavers. A queued client who disconnects is removed before it reaches the model, so the GPU never works for nobody.

The queue lives in gateway memory, not Redis: it protects this model server's capacity, and it must keep working when Redis is down.

7When Redis fails

Fail open or fail closed is a product decision.

ChoiceRedis down meansGood for
Fail openRequests pass uncheckedAvailability
Fail closedEverything is rejectedStrict limits, e.g. login attempts

The gateway fails open. That's safe here because backpressure doesn't need Redis: a Redis outage costs fairness between clients, not protection of the GPU. Every fail-open is counted in /health, because a silent fail-open is a limiter that's been broken for days.

Unplanned demo

Docker quit mid-measurement. The rate-limit test showed no 429s at all, and /health showed why: Redis down, 21 requests let through and counted.

8The slot that never comes back

Cleanup has more exits than you think.

Every request that gets a slot must give it back exactly once. Never: with a cap of 1, the gateway is stuck for good. Twice: two generations run at once.

The natural place for the release is a finally in the streaming generator. But Starlette may never start iterating the generator if the client leaves early, and then its finally never runs. So the release wraps the whole response instead, shielded from cancellation like Week 2's cleanup.

Found by breaking the code

Replacing the disconnect watcher showed that a watcher which crashes was treated as "client left", silently dropping a live request. It now raises a visible error.

What it does not do

Total output stayed about 55 chunks/s in every run. Backpressure adds no capacity: it stops accepting work that can't be done in time. The bare server eventually served all 16; the gateway served 3 and told 13 to come back. More capacity is continuous batching, in Month 3.

10Tests, CI, Docker

Steps 8 and 9.

50 tests

Against a real Redis and a fake model server with exact timing. Each guarded behaviour was broken on purpose to check its test fails.

Redis in CI

A GitHub Actions service container. REQUIRE_REDIS=1 turns "Redis missing" into a failure, not a silent skip.

Compose smoke test

docker compose up --wait on GitHub, then health, a streamed answer and a 429 through the real containers.

Two images, two triggers

A paths filter per image, so a gateway change doesn't rebuild the 9 GB model image.

Inside compose the gateway finds Redis at redis:6379 and the model at fake:9000: service names, not localhost. Only the gateway publishes a port.
