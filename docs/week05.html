A model registry the gateway listens to

Month 2 starts with the problem ML systems are known for: they fail silently. A worse model throws no exception; it just answers worse. The first defence is knowing exactly what is live, refusing what wasn't tested, and being one command away from the last good version. This week: an MLflow registry on Postgres, a promotion gate, rollback, and a gateway that switches without a restart.

The big picture

Three separate steps: score and publish, decide what is live, serve it.

Java analogy

The registry is Nexus or Artifactory for model settings: immutable, numbered versions. The champion alias is the current symlink in a releases folder: deploying and rolling back are pointer moves, nothing is rebuilt.

1What a version is

A settings card plus a score sheet, not a weights file.

Retraining is out of scope, and 16 GB of weights don't belong in an artifact store on a laptop. So a version is the settings card the gateway serves with (model_id, temperature, max_tokens, system_prompt) and a score sheet: a 10-prompt keyword eval and time to first token. Many LLM teams version prompts and configs this way.

VersionCardPass rateTTFT p50Tag
v1Qwen2.5-0.5B-Instruct, temperature 0.790%69 mseval=passed
v2Qwen2.5-1.5B-Instruct, temperature 0.3100%116 mseval=passed

The bigger model got 17 × 23 right (v1 said 481), at about 70% more time to first token. The score sheet puts that tradeoff on the record before anything ships.

What a keyword eval can't see

v1 called Romeo and Juliet "the novel" and still passed: "Shakespeare" was in the answer. A keyword eval catches a broken or much worse card, not subtle quality loss. That is what Week 7's drift and quality signals are for.

2Publishing is not deploying

Registering a version and making it live are different commands.

register.py scores a card, logs it as an MLflow run and registers a new version tagged eval=passed or eval=failed. It never touches the champion alias. release.py promote N does that, and refuses any version not tagged eval=passed.

A CI/CD idea

"Build once, deploy many": the artifact is built and published once; which one runs is a separate, deliberate decision. The eval tag is the quality gate, like a branch rule that blocks merging until CI is green.

CommandResult
promote 2 (eval=passed)champion → v2, old champion → fallback
promote 3 (eval=failed)refused, nothing moves
promote 2 againno change, and fallback is not overwritten

MLflow registry stages (Staging/Production) are deprecated; aliases and tags replace them. MLflow also keeps no history of where an alias pointed, so every move tags the version: promoted_at, promoted_by, rolled_back_at, rollback_reason.

3Rollback, and two calls that can't be atomic

Order the calls so that every in-between state is safe.

rollback moves champion back to fallback and then clears fallback. The version just rolled away from is suspect, so it must not be one command from going live again; a second rollback is refused until a good version is promoted.

That is two API calls, and MLflow can't run them as one transaction. So the order matters:

CommandOrderCrash in between leaves
promoteset fallback, then championold champion still live. Harmless
rollbackset champion, then clear fallbackgood version already live. Harmless

A test makes the fake registry crash at each step and checks the bad version is never left live.

Java analogy

The same thinking as a @Transactional method that calls two remote services: there's no rollback across them, so you order the writes so a partial failure is safe.

4The gateway listens

Resolve at startup, switch on reload, one card per request.

  • Startup, fail fast. With the registry on and no usable card there is nothing correct to serve, so the gateway refuses to start and the container is restarted. Like a Spring Boot app that won't start without its datasource.
  • One card per request. Each request reads the card reference once. A reload swaps the reference; requests already running keep the card they started with. The card is a frozen dataclass: an immutable object behind an AtomicReference, in Java terms.
  • What the card controls. model always; max_tokens capped; temperature and the system prompt unless the caller chose their own.
  • Never block the event loop. The MLflow client is synchronous, so it runs on a worker thread (Week 1's lesson).
  • An admin endpoint needs a secret. /admin/reload changes what every user gets, so it needs X-Admin-Token, compared in constant time. No token configured means the endpoint is off.
What reload doesn't do yet

The card's model_id goes into each request, but the Week 2 model server has one model loaded. Switching between two running model servers, with zero dropped requests, is Week 6.

5When MLflow is down

A default that suits a batch job hangs a server.

SituationResult
Client call, MLflow unreachable, default settings247 s of retries, then an error
Gateway startup, MLflow unreachable, retries capped to 0exits after 2.3 s (mostly Python starting)
/admin/reload, MLflow stopped503 in 4 ms: "Still serving v1", /health says degraded
MLflow back, reload again200, error cleared
Measured

For a training script, retrying for four minutes is reasonable. For a gateway it means a registry outage blocks deploys for four minutes per attempt. The gateway sets MLFLOW_HTTP_REQUEST_MAX_RETRIES=0 unless told otherwise, and relies on the orchestrator to restart it and on last_good to keep serving.

A failed reload is loud: a 503 with the reason, a warning in the log, degraded on /health. Falling back silently would hide exactly the kind of failure this month is about.

6Fakes that lie

A test double is only as good as its match with the real thing.

The unit tests use fake registries: dicts behind the same method names as MlflowClient, so they run in half a second with no server. Two mismatches turned up when the code met the real server:

Bug in the fake

MlflowException("...", error_code="RESOURCE_DOES_NOT_EXIST") silently becomes INTERNAL_ERROR: the argument must be the protobuf enum constant. The fake raised the wrong error, and the code under test correctly refused to treat it as "not found".

Real behaviour you'd guess wrong

A missing alias is INVALID_PARAMETER_VALUE, not RESOURCE_DOES_NOT_EXIST.

So CI asks the real server for both error codes and fails if they ever differ from what the fakes assume.

7CI against a real registry

The first CI job with state that must survive a restart.

  1. Unit tests: promote/rollback rules on the fake registry.
  2. Start MLflow + Postgres from the same compose file used locally.
  3. Register three cards with register.py's own code (no scoring: no GPU in CI), and check eval=failed is refused.
  4. docker compose down, then up: volumes kept, containers new.
  5. Check champion survived, resolve_champion() returns v2 from the real server, and the error codes match the fakes.
  6. Start the gateway against it: serves v2; reload without the token gets 403; roll back, reload, now serves v1.
A CI/CD idea

CI installs a light dependency group (week05-registry: the MLflow client, no torch), the same split as Week 2's week02-serve. The scoring half of register.py imports torch only inside its functions, so the publishing half runs in CI.

The price of the client

The gateway image went from 293 MB to 412 MB with mlflow-skinny, for two HTTP calls. Accepted for now (the supported client, pinned to the server's version); a small hand-written client for those two REST endpoints would take it back out.

Deferred to Month 4: promotion as a GitHub Actions workflow with a required approval, once there's an MLflow server CI can reach.
