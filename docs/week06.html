Moving traffic between model servers without dropping a request

Week 5 made the registry decide which settings are live. But a new model version usually means a new model server, and swapping servers is where users get hurt. This week the gateway runs in front of two servers, blue (serving now) and green (the new one), and moves traffic between them with one admin call: gradually, reversibly, and without cutting off a request already streaming.

The big picture

Two servers stay up. The gateway decides, per request, which one answers.

Java analogy

A weighted load balancer whose weights change at runtime, like Spring Cloud LoadBalancer with a weight you can turn from an admin endpoint. The weights live in one immutable object, and changing them is one AtomicReference.set().

1One number decides the side

TrafficSplit(green=10) and choose(split, r) in gateway/router.py.

A split stores only green's percent; blue's is 100 - green, so the two can never disagree. For each request the gateway draws r = random.random() (from 0 up to, not including, 1). Green owns the bottom slice of that range:

return GREEN if r * 100 < split.green else BLUE

Random numbers are uniform, so a 10% slice gets about 10% of requests, with no shared counter, no lock and no coordination between gateway copies.

The boundary belongs to blue

With <= instead of <, green=0 would still send a request to green whenever r is exactly 0.0: "rolled back" would not mean "nothing goes to green". A test feeds 1000 evenly spaced values of r and requires exactly 10 × green of them to land on green, which catches that off-by-one.

Java analogy

r is passed in rather than drawn inside choose(), for the same reason you inject a Clock instead of calling Instant.now(): tests can pick the exact values.

2Pick once, finish there

Changing the split never moves a request that has already started.

The gateway calls choose() once, near the start of the request, and uses that side until the stream ends. A new split is one reference assignment: requests already running keep the side they picked; requests that start after it use the new one.

t=0 s   request A starts   -> blue, starts streaming
t=1 s   POST /admin/traffic {"green": 100}
t=2 s   request A still streaming from blue    (it never asks again)
        request B starts   -> green

A test does exactly this: it starts a 1-second stream on blue, switches to 100% green partway, and checks that every chunk came from blue and the stream reached [DONE]. Meanwhile /health shows blue with in_flight: 1, draining. When that reaches 0 with blue's weight at 0, blue is safe to stop.

3One admission limit per server

Each server has its own capacity, so each gets its own in-flight cap and queue.

Week 3's admission control caps how many requests the model server works on at once. With two servers, a single shared cap would be wrong: while blue drains its last long streams, a request headed for an idle green would wait behind them, or be turned away with a 503.

So each side has its own pooled client and its own admission limit. To check the test really guards this, the code was broken on purpose (both sides sharing blue's limit, one slot, no queue): the test failed at the green request, as it should.

Java analogy

The bulkhead pattern (Resilience4j Bulkhead): one isolated pool per downstream service, so one busy dependency can't starve calls to another.

4Each server gets its own settings

Two more registry aliases: blue and green.

Week 5's settings card (model, temperature, token limit, system prompt) now comes per side. Each server follows its own alias, and champion becomes the record of what was officially released. With one server, nothing changes from Week 5: blue serves champion.

StepCommandUsers see
Deployrelease.py deploy 2 --to green, then POST /admin/reloadnothing yet: green has 0% of traffic
CanaryPOST /admin/traffic {"green": 10}1 in 10 new requests on v2
Promote{"green": 100}, then release.py promote 2all new requests on v2; blue drains
Rollback{"green": 0}all new requests back on v1, instantly

deploy uses the same gate as promote: only versions tagged eval=passed can reach either server.

All or nothing

A reload fetches every side's card before changing any. If green's new card is fine but blue's alias is missing, neither side changes and the answer is a 503 saying "Still serving blue v1, green v2". A half-applied reload would quietly put one side on a new version while you believe the reload failed.

Why two assignments in a row are safe here

The reload sets blue.card, then green.card. No request can run in between: asyncio switches tasks only at an await, and there is none between the two lines. In Java, where a thread can be pre-empted anywhere, you would need a lock or one AtomicReference holding both.

5Measured: restart vs Blue/Green

50 streaming requests per second for 10 s, switching blue → green at 4 s. Three runs each.

How the switch is doneFailed requestsUsers affected forp99 (successful)
Naive: change UPSTREAM_URL, restart the gateway78–80 of 500 (16%), all "connection refused"1.55 s424 ms
Blue/Green: POST /admin/traffic {"green": 100}0 of 5000 s424 ms
Canary: green 10% → 50% → 100%, 2 s apart0 of 5000 s425 ms
  • No running stream was cut off, even in the naive case: on SIGTERM, uvicorn stops accepting connections but lets running requests finish. Every failure was a new request arriving while nothing was listening: 0.5 s of draining plus 1.1 s of starting.
  • This is naive at its best. Only the gateway restarted; both model servers stayed up. A real "stop v1, start v2" restarts the model server, and loading weights takes far longer than starting Python. Blue/Green stays at zero because green is warm before it gets traffic.
  • The fake servers stream 20 chunks 20 ms apart (400 ms), so the gateway's overhead is about 24 ms in every mode.
How the load is generated matters

The benchmark is open-loop: a request starts every 20 ms whether or not earlier ones have finished, like independent users. A closed loop, where each worker waits for its last reply, sends fewer requests during an outage, so it would under-count exactly the failures being measured.

Checking the tool first

Two answers can be worked out by hand. Blue/Green at 4 s must give exactly 200 requests to blue and 300 to green: measured 200 / 300. Canary must give about 2 s × 50 × (10% + 50% + 100%) = 160 to green: measured 158.

6CI tests the deploy, not just the code

The test-week06 job runs real traffic through a real switch on every push.

Blue/Green switch under load0 requests failed (--max-failed 0)
Canary 10 → 50 → 100 under load0 requests failed
Control: naive restart under loadat least 1 request failed (--min-failed 1)
A CI/CD idea: test the test

A benchmark broken in a way that always reports zero failures would make the first two checks pass while measuring nothing. The control step requires the same tool to see the outage a restart causes. It's the same idea as a smoke alarm's test button.
