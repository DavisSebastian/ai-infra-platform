Catching a model that fails silently

A worse model throws no exception. Every request still returns 200, latency looks normal, and the dashboards stay green; the answers are just different. This week the gateway records what it serves, and a drift check compares recent traffic with a known-good baseline to answer three questions: has anything changed, did the users change or the model, and is it worth acting on?

The big picture

The gateway only writes things down. A separate job does the statistics.

1Record, don't compute

One record per request, written off the request path.

When a request finishes, the gateway puts its raw bytes and timings on an in-memory queue and moves on. A background task parses the prompt and answer and writes one record to a Redis stream (side, card version, status, timings, prompt, answer). Requests never wait for it, and a full queue or a Redis outage is counted, never felt: the request already succeeded. Measured: about +1 ms at p50, p99 within run-to-run noise.

Java analogy

Logback's AsyncAppender with neverBlock=true: a bounded queue in front of a slow appender that discards events rather than making the caller wait.

Time to first token said 2 ms

The model server sends a role-only event ({"role": "assistant", "content": ""}) the moment it starts, before generating anything. Timing the first chunk measured time to first byte, which stays flat however slow the model is. The gateway now records when each chunk arrived, and the writer finds the first one carrying text: 34 ms.

2Text becomes numbers

Statistics need numbers, so every record becomes a row of them.

KindFeatureCatches
inputprompt_wordslonger or shorter questions
inputprompt_embeddingusers asking about different things

outputanswer_empty, refusala model returning nothing, or refusing

An embedding turns a sentence into a list of numbers (384 here, from the small all-MiniLM-L6-v2 model) so that sentences with similar meaning get similar lists. "What is the capital of Australia?" and "Which city is Australia's capital?" scored 0.93 similarity; an Everest question scored 0.16. If today's prompts land in a different region of that space, users are asking about something new, with no list of topics needed.

3Comparing two windows

Whole distributions, not averages. Evidently picks the test.

  • Numbers (answer words, TTFT): the Kolmogorov–Smirnov test measures the largest gap between the two cumulative distributions and gives a p-value: how likely is a gap this big by chance? Drift if p < 0.05.
  • Yes/no (refusal, empty): a Z-test of proportions, same threshold.
  • Embeddings: label baseline prompts "old" and current ones "new", train a small classifier, and measure how well it tells them apart (ROC AUC). About 0.5 means it can't: same traffic. If a model can tell last week's questions from today's, the questions changed.
Calibrate before you trust a default

Evidently's default calls embedding drift when AUC > 0.55. On 200 random splits of the everyday prompts (no drift by construction, 150 vs 150), that fired 11% of the time. Its bootstrap option (beat 95% of AUCs from random labels at this sample size) fired 6%, so that's what the check uses.

4Blue is the control group

Drift says "different". Blue/Green tells you whose fault it is.

Answers get longer when users ask harder questions; rolling back for that would be wrong. During a canary the split is random per request, so blue and green serve the same users at the same time. That gives a built-in control group:

Green vs baselineGreen vs blueDiagnosis

Canary analysis

Comparing the canary with instances serving the same traffic at the same time is how automated canary systems decide (Spinnaker's Kayenta, for example). A baseline from last week can't separate "users changed" from "model changed"; a same-time control can.

5Two signals before an alert

decide(): insufficient_data / ok / warn / alert. Week 8 rolls back on alert.

Each check fires by chance about 1 time in 20. With four output checks, acting on any single one would roll back for nothing about 1 run in 5; requiring two brings that to about 1 in 71. So an alert needs two output checks differing from blue, or one confirmed by both comparisons (vs blue and vs the baseline). Input drift alone is only a warning, and below 50 records nothing is judged.

Significant is not the same as important

The same model on the same Mac three days later: TTFT median 33.6 → 34.2 ms (+1.8%), and K-S gave p < 0.0001, because the values are tightly clustered. A p-value says a difference is real, not that it matters. TTFT now also needs the median to move at least 20% (a different model moved it 68% in Week 5).

7Things that bit

  • Repeated prompts faked drift. Sending each prompt twice put the same prompt in both the classifier's training and test halves, so it memorised them: AUC 0.51 → 0.68 with nothing changed. Each prompt is now sent once.
  • A crude embedding false-alarms. The CI stand-in (words hashed into buckets) said "drift" (AUC 0.59) on holdout vs baseline, where MiniLM said 0.506: the same kinds of questions, in different words.
  • Evidently 0.7.23 doesn't import with pandas 3. pyproject.toml pins pandas<3, with the reason written next to it so nobody "tidies" it away.
A CI/CD idea

The test-week07 job runs 29 tests on the committed baseline window with the stand-in embedding (no torch, no model download). Each changes one thing about real traffic and checks that only the matching check notices, and that unchanged traffic raises nothing.

Limits

Drift says "different", not "worse"; the refusal and empty-answer checks are crude proxies for quality. Windows of about 75 per side are small. And records keep prompt and answer text, which is why the log is off by default.
